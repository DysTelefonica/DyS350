# Release v0.0.4

Date: 2026-11-18
Tag: `v0.0.4`
State: the state of the environment of PROD (`DyS350_TF_E_PRO`) and of `main`.

## What was modified

### The table of roles matches the JSON

The role table of DEV/CERT and of PROD was reconciled with the JSON that governs each expediente.
The inventory of the morning showed that the table had drifted away from the JSON in two ways: the
rows of a person that the JSON does not describe, and the **repeated copies** of a row (829 of them
in DEV/CERT and 55 in PROD), which the rule of the flow could not remove because the key of the
desired set is `usuario + '-' + IDRol` and a copy answers the same key.

| | DEV/CERT | PROD |
| --- | --- | --- |
| Rows before | 1357 | 233 |
| Rows after | 317 | 136 |
| Repeated copies | 829 -> 0 | 55 -> 0 |
| Rows that no JSON explains | 3 | 60 |

The rows that no JSON explains were left untouched: three in DEV/CERT (the expediente `1269` has
no processed JSON at all) and sixty in PROD (twenty-two expedientes whose JSON was never ingested,
so the JSON does not speak for them). They need a business criterion, and the record of the change
is in [the reconciliation of the table](../changes/role-table-reconciliation-2026-11-18.md).

### The flow removes the copies of a role row

The child flow `E2E_AltaExpedientes_Modulo1` of PROD now deletes a row that is a copy of another
row of the same expediente with the same person and the same kind of role. The person stays in the
group of that kind, because a copy is not a change of person.

| Flow | Before | After |
| --- | --- | --- |
| `E2E_AltaExpedientes_Modulo1` (the child) | `97D20BA24E01CEEB3DFF506C532FF3BE0F26C1EBE41E100AC73C0E0A51B5A1E9` | `A878F9225CD981149D1CF365D49FD884046F7C94358FEF06C02FB221F23A84E2` |

The promotion was a **port**, not a copy: the wiring of PROD was kept and the difference against the
definition that was live in PROD is exactly the two paths of the phase.

**Measured in PROD with a controlled case**: a copy of a role row was inserted by hand and the JSON
that describes the row was processed again; the child run finished **Succeeded**, the copy was
deleted, the row that the JSON describes was not rewritten and no action of the run failed. The data
of the case was removed afterwards. The record of the promotion is in
[the record of the promotion](../changes/prod-role-duplicate-removal-2026-11-18.md) and the
evidence of the work in the branch `DEV/CERT`, in `docs/tests/`.

## What was attempted and how it ended

The reconciliation of the table was applied with a plan computed outside the environment, and the
plan was applied with the REST API of SharePoint. Two things went wrong on the way and both are
recorded:

- The first two batches of the plan were **executed twice** because the cursor of the batch did not
  persist between calls. The second execution repeated the deletions (the deletion of a row that
  was already deleted answers a 404 and changes nothing) and it created eighteen rows a second
  time. The plan was rebuilt from the live state and removed those copies; the final verification
  found no repeated copy in either environment.
- The classification of the rows had to be corrected once. A row with an empty user matches an entry
  of the JSON with an empty user, because the flow matches the rows by the key
  `usuario + IDRol`. Reading the empty user as "not described" marked 1278 rows of DEV/CERT as
  deletable, which was wrong; the rule is applied as the flow applies it.

The additions to the groups that failed are not a failure of the change: twenty of them name people
who are not users of the tenant (`responsable.calidad.*@empresa.com` and the like), so the row of
the role exists with the person of the JSON and the person cannot become a member of the group.

## What is left open

- The **60 rows of PROD** (and the 3 of DEV/CERT) that no JSON explains still need a business
  criterion: nothing in the environment says what they should be.
- The identifier of a role row still changes when the person of a role changes: the row is deleted
  and created again by the flow.
- A member of a group whose row was deleted by other means stays in the group: the flow only takes
  out the members of the rows it deletes.
