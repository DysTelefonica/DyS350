## Review the narrow change

Action path: `actions/Try_-_Procesar_ExpedientesJSON/actions/Existe_ExpedienteJSON/actions/Expediente_ya_Aprovisionado/actions/Actualizar_Expediente_Sistema`.

The [generator](prepare.cjs) makes exactly three structural changes:

1. Add `Validate_Expediente_Title_Sync` after the existing `Obtener_Expediente_del_Sistema` lookup.
2. Run the existing provisioned-record condition only after that guard succeeds.
3. Add `item/Title` to the existing `PatchItem`, preserving every other mapping, connection, business-key lookup, downstream dependency and error handler.

The guard allows a missing/null/string source `titulo` and at most one destination match. It adds no business-ID restrictions. Missing/null/whitespace source preserves the current destination value; a valid title is copied verbatim, including its original whitespace, and can repair a null/missing destination title. Duplicate destination matches or invalid title types stop the destination update. No record is created for an empty lookup. No spelling substitution or incident ID is embedded in the patch.

**Not a transaction:** the guard runs after the existing `Actualizar_ExpedienteJSON` write. Rejection does not undo that write, and later processing can be skipped through existing failure handling. The same title is value-idempotent, not a zero-write guarantee: the original update still writes its other fields on each ingestion. Concurrency, event ordering and ETag conflict control are unchanged; an older concurrent replay can still win. For blank input the current title is re-sent, not omitted from the update.

## The change trace (phase 7)

[prepare-change-trace.cjs](prepare-change-trace.cjs) builds on the published centralized mapping (pinned canonical hash `84FABEA2…`) and makes the log of an ingestion say what changed: for every column that the flow patches in the staging list, the log carries the previous value and the new one. The generator asserts that the thirty seven columns of the comparison are exactly the thirty seven `item/*` columns of the patch, so the trace and the write cannot drift apart.

**The comparison is between the row before the write and the row after it, both read from the list.** The write waits for the read of the row it overwrites, the trace waits for the read of the row the write left, and both reads point at the same item: the one whose id is `first(body('Filtrar_resultados_por_Expediente'))?['ID']`, which is the id the patch writes. Reading the two sides from the list is what makes the comparison exact. SharePoint keeps a date as the datetime of the day (`03/04/2026 00:00:00` becomes `2026-03-03T23:00:00Z`), a boolean as the text `True`, the members as the text `Nombre - correo;` and a number as a number; comparing the JSON with the stored row would mean re-implementing those rules in the template language, and the first attempt at that failed at runtime: `substring` on an empty value throws, so every existing expediente was logged as failed. Reading the row twice means the comparison only has to answer "is this the same text", which is the one question the platform can answer without failing.

**The trace is written in chunks.** The platform accepts at most **8,192 characters per expression** ("Characters per expression", [flow definition limits](https://learn.microsoft.com/en-us/power-automate/limits-and-config)). The comparison of the thirty seven columns is 15,211 characters, so one expression for the whole trace would be refused when the flow is saved, the way the circular dependency of phase 2b was refused. The generator splits the comparison into three expressions (`Calcular_Cambios_1` to `Calcular_Cambios_3`), the longest of them 5,784 characters, under a budget of 6,000 that leaves room for a later edit of one field, and the log concatenates them.

**The comparison only uses functions that cannot fail on an empty value** (`equals`, `string`, `coalesce` and `concat`), so a mistake in the comparison cannot break an ingestion: the worst it can do is to report a change that is not one. The tests refuse any other function in the generated expression.

Two rules of the platform shape the candidate and both are checked by the tests: an expression may only read an action that is in its `runAfter` path (the first publication was refused with `The inputs of template action 'Calcular_Cambios_1' cannot reference action 'Leer_ExpedienteJSON_Antes'`), and an action may only wait for an action that comes before it (the trace comes after the write, and the write waits for the read of the row it overwrites).

The [tests](prepare-change-trace.test.cjs) check the pinned source, that the candidate closes no dependency cycle, that every expression of the candidate is under the limit of the platform, that the whole trace as one expression would be over it (the reason the chunks exist), that the chunks cover every column once and in the order of the table, that the comparison only uses the functions that cannot fail, that both reads point at the item the write patches, that the branch waits for the members and for the row of the previous ingestion before the branch starts, that the names of the actions are under the limit of the platform, that the log carries the trace and that nothing else of the flow is touched: 34 tests passed and 0 failed. Eleven of them evaluate the generated expression with a small evaluator of the template language, so the trace is proved with the values of a real ingestion: a title that did not move is not reported, a title that moved is reported with its previous and its new value, a date is compared as the list keeps it, a column that was never filled is a change, a column that had a value and now is empty is a change, no comparison fails with empty values, the log writes what the chunks found and the expression that read the chunks with `body()` wrote nothing even with a change. Outputs go only to the ignored `.atl/project-title-sync/change-trace-20261115/` directory. The generator performs no network or cloud operation.

The candidate is **applied in DEV/CERT** (published definition `062C26A1…`, the exact output of the generator) and **measured**. The write and the counts are right (`Total 3, Nuevos 0, Actualizados 3, Fallidos 0`) and the log carries the trace: `; ImporteContratacion: 111222.33 -> 555555.55; Observaciones: …[RF14…] -> …[RF13…]` for the expediente that moved, and an empty text for the two controls.

The trace was empty for three reasons in a row, and each of them was a fact of the platform and not of the comparison: the first attempt compared the JSON with the stored row re-implementing how the list keeps a date, and `substring` on an empty value threw; the second compared the two rows with the wrong accessor of the read; and the third had the right comparison in the right place and threw the answer away, because **the log read the chunks with `body()` and a Compose action has no body** (`body()` of a Compose is empty and `concat` skips the arguments that are nothing). The last one is the rule worth keeping: read the result of another action with `outputs()`, never with `body()`.

## The ordering guard (phase 8)

[prepare-ordering-guard.cjs](prepare-ordering-guard.cjs) builds the decision of the phase E on top of the published parent flow of DEV/CERT (2A2E04E4...): an ingestion whose JSON is older than the one already applied to an expediente must not overwrite it.

**The guard lives in the parent**, which orchestrates and decides whether an expediente is processed at all: when the file is old, the whole branch of the expediente is skipped (the staging row, the application list, Dataverse, the roles, the milestones and the suppliers). The child flow, which reconciles, is not touched by the decision.

**The comparison is per expediente**, never per file, and it is made with the fourteen digits of the two instants, as a number: `int(concat(substring(...)))` turns an ISO 8601 UTC instant into a number that sorts the way the time does, without asking the platform to compare dates, which is the thing the platform does badly. The comparison lives in a scope with a catch: when it cannot be made the file is applied (fail open), because a guard that breaks the ingestion is worse than a guard that does nothing.

**The state is a file of the library of the logs**, one per expediente (`estado_<id>.json`), with the key of the generation time of the last JSON applied to it: **no flow of the environment can write a new column of a list**, because the definition of the operations that the connection of both flows carries is a copy made before the column existed, and the platform refuses the parameter of the write (`The API operation does not contain a definition for parameter 'item/ClaveGeneracionJSON'`). The parent writes files without problem, so the state is a file. [prepare-ordering-state.cjs](prepare-ordering-state.cjs) is the part of the phase that belongs to the child (the key travelling in a new input of its trigger); it was not needed with the state in a file and it is not published.

The phase is **closed**: the guard finds the file of the state with the form of the path that the REST routes (`_api/web/lists/getByTitle(<biblioteca>')/RootFolder/Files('<nombre>')/$value`), the parenthesis being what makes the difference, and the comparison lives in its own action, because the platform only refuses a badly parenthesised expression when it evaluates it, in the run ("The template language function 'if' expects three parameter ... The function was invoked with '1' parameter(s)"). The tests of the generator count the arguments of every function of the guard, with the expression that the platform refused as a fixture. **Measured on 2026-11-16:** the run of the new file applied the three expedientes of the case (`Total 3, Nuevos 3, Actualizados 0, Fallidos 0, Antiguos 0`) and the run of the old file skipped the three of them (`Total 3, Nuevos 0, Actualizados 0, Fallidos 0, Antiguos 3`), and the row of the staging list keeps the values of the new file. **Published:** `6081A1D1...` in the parent. The promotion to PROD is a separate step, with its own authorization, and it was not executed. The record of what was measured and of the rules of the platform that shaped the candidate is in [the report of the phase](../../docs/tests/dev-ordering-guard-2026-11-16.md).

## Publishing a candidate and cleaning the environment of DEV/CERT

The definition of a candidate is published in the row of the flow in Dataverse (`workflows(<id>)` with the whole `clientdata`), and the proof is the read-back by hash. **The token of Dataverse does not need a new sign in**: the maker portal of the session already calls Dataverse, and the bearer token of those calls has the audience of Dataverse, so it can be captured from the requests of the portal and it publishes and reads the row of the flow. The authorization code of the browser session is the route when it has to be renewed from scratch: `https://login.microsoftonline.com/<tenant>/oauth2/authorize?client_id=1950a258-227b-4e31-a9cf-717495945fc2&response_type=code&redirect_uri=https%3A%2F%2Flogin.microsoftonline.com%2Fcommon%2Foauth2%2Fnativeclient&resource=https%3A%2F%2Forge4f220a2.crm4.dynamics.com` answers the code in the URL of the native client page, and that code is exchanged for a token of the audience `https://orge4f220a2.crm4.dynamics.com` with the **first** version of the endpoint (`resource`, not `scope`: the second version answers a token for Azure AD Graph and Dataverse refuses it with `401`). The device code of `login.microsoft.com/device` is the alternative, but the form of that page does not accept the click of the tooling.

The rows of the controlled data of SharePoint are read and deleted with the session of the browser and the request digest of the site: `POST /_api/contextinfo` for the digest, then `GET /_api/web/lists/getbytitle('<list>')/items?$filter=<key> eq <id>` for the rows and `POST` with `X-HTTP-Method: DELETE` and `IF-MATCH: *` for the deletion. The site of CERT is a classic site and it has no recycle bin, so the deletion is permanent. The token of Dataverse does not reach SharePoint: the audience of the site is `00000003-0000-0ff1-ce00-000000000000` and the API answers `401` with it.

The browser session can also run JavaScript, which is what makes the deletions and the uploads possible without the operating system dialogs: the tooling runs code in the page, the session sends the cookies and the code can ask for the digest of the site. The upload of a file through the REST API of the site is refused (`Files/add` answers `InvalidClientQueryException`), but **the web part of the library does accept the payload**: open the menu "Crear o cargar" → "Carga de archivos" and set the file on the input `input[data-automationid="commandFileInput"]`; the toast reads "Cargado `<file>` en `<library>`". The trigger of the parent flow polls, so the run starts about a minute later. The run details are read with the token of the portal: `GET https://emea.api.flow.microsoft.com/providers/Microsoft.ProcessSimple/environments/<env>/flows/<id>/runs/<run>?$expand=properties%2Factions,properties%2Fflow&api-version=2016-11-01` answers the actions of the run with the links of their inputs and outputs, and those links carry the evaluated input and output of every action.
